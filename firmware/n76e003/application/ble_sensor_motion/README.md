# N76E003 抗運動心率試驗版

已完成固定點 C 演算法、CSV／合成測試、SDCC 整套韌體建置與 s51 指令量測。
**可以放入 N76E003，但尚未燒錄驗證；目前改善的是運動候選排除與通道選擇，不是任意運動下的波形還原。**
原本 `ble_sensor_hr` 的演算法與主程式沒有被替換。

後續已完成 [12組TROIKA公開跑步資料測試](public_test_results/REPORT.md)：完整模式整體有效比例14.49%，
按實驗流程粗分的跑步區段僅8.85%；有效輸出也仍有大誤差。這版尚未達到運動時持續可靠輸出的目標，不能只看下面的合成測試。

## 實作

- 核心：`../ble_sensor_hr/source/ppg_motion_hr.h`，純整數、無 heap、無 FFT、無完整波形視窗。
- 本專案 `source/main.c` 啟用 `ITAP_MOTION_HR`，沿用 `ble_sensor` 的 UART、I²C、BM7701 連線與啟動流程。
- PPG 每約28 ms處理一次；三軸 ACC 26 Hz、±8 g、保留重力，演算法內移除基線。gyro 停用。
- OLED 與正式手錶相同，P3.0切換PPG／IMU／波形三頁（2026-10-25）；文字頁快取改為每行2 B雜湊碼，才放得進XRAM。OLED每筆PPG約多佔3～4 ms I2C，與ACC 2 ms輪詢共用匯流排，P1.7可關閉螢幕停止佔用。這是獨立試驗配置，不更改正式架構規則。
- BLE 名稱 `BLE_watch_ITAP`，PPG msgType=0x11，約每5秒送一次本機心率結果；失去有效性時盡快送0。
  ACC 使用0x13封包，讀取26 Hz但對 HUB 上報1 Hz。不適用只接受 `BLE_capture_ITAP` 的擷取頁。
- PPG封包 byte11 是自算 HR；status=2 表示自算 HR 有效，不再表示模組 D3 的有效性。
  其他模組衍生欄位（SpO2等）未重新計算，不可用此 status 判定它們有效。
- 不上傳完整波形；若要收集演算法驗證資料，仍用 `ble_sensor_capture`。

## 演算法

1. 兩路 PPG 各自做基線移除、平滑與短／長遞迴平均的動態波峰門檻。
2. 每路只保存最多16個心搏間隔；每5秒以中位數排除偏離超過約16.7%的間隔。
3. 三軸 ACC 各自追蹤有遲滯的正向過零週期，至少數個穩定週期才作動作頻率參考。
4. PPG候選落在動作週期附近（12.5%），或半頻／倍頻附近（8.3%）時，視為有歧義。
5. 兩路都可信且心率相差不超過約10%時融合；只有一路可信而另一條無效／接近動作頻率時，可選擇可信通道並降低品質分數。
6. 僅對新的有效結果做 `2/3 當次 + 1/3 前次輸出` 的輕量平滑；兩次相差超過12 BPM直接採新值。
   無效結果清除平滑狀態，絕不把舊心率偽裝成新量測。

統計區間不重疊。第1個5秒區間是暖機，最早有效結果約在10秒。
這是針對約35.7 Hz PPG調整的原型，時間常數不是自動適應任意取樣率。
軌頂／軌底、無接觸、時間倒退／重複、PPG >100 ms缺口會重置；韌體入口另檢查序號缺口。
ACC不新鮮、>100 ms缺口或每5秒不足80筆時，要求 ACC 的模式不產生有效HR。

`quality` 是間隔一致性指標（單通道選擇固定降為60），不是醫療準確率。
reason：0有效、1暖機、2訊號不足、3動作頻率歧義、4雙路不一致、5加速度缺失、6接觸／時間缺口。
`mh_reset(&state,1)` 為完整ACC輔助模式；傳0僅供舊PPG-only CSV回放，不代表無ACC也有相同抗運動能力。
呼叫者須在主迴圈依取得順序呼叫 `mh_acc`／`mh_ppg`，使用共用毫秒時間戳的低16位；不可從 ISR 呼叫。
超過16-bit時間範圍的停頓、裝置重啟或已知序號缺口，呼叫者須主動reset，避免回繞歧義。

## 資源量測（2026-10-18，Nuvoton SDCC 4.2.6 large model）

| 項目 | 結果 |

| 演算法profile程式 XRAM（含編譯器暫存、事件索引與測試結果） | 見重新執行產生的 `.mem`；不是只算sizeof |

| 分析＋profile迴圈負荷 | **約0.7212–0.7578 MIPS** |

| clean測試中單筆ACC最大指令數 | **9,945** |

`test_results/profile.json` 保存結果。每個profile使用12秒合成輸入，共741筆 PPG／ACC事件。
以 s51 `state` 的動態 `Inst` 差值除以12秒，得到等效每秒所需指令量；
包含測試程式從code memory取事件與dispatch，不包含BLE、I²C、UART中斷和真實等待。
六個情境的host與8051結果逐項相符，clean測試另逐筆以進入／退出標記量測指令數。
這些是已測試路徑的最大值，不是形式化的所有輸入最壞執行時間證明。

s51使用經典8051週期，**不能將它列出的執行秒數直接當作N76E003的1T執行時間**。
以16.6 MHz及「平均每指令2–4 clocks」作條件估算，分析約占9–18% CPU，
42,242指令約5.1–10.2 ms；這是假設值，未量測實際CPI或整套主迴圈截止時間。
profile未啟用實機中斷；觀察到的SP最大0x42也不能當作整套韌體最大堆疊。
上板後仍須量測處理時間、ISR／主迴圈漏樣與堆疊高水位，才能確認播放／BLE整合以外的實際穩定性。

## 測試結果

合成資料每組60秒，5秒暖機後通常10個可評估輸出；結果檔包含暖機，因此 `windows=11`。
誤差只對有效輸出計算，同時列接受數，避免以大量拒絕掩蓋誤差。

| 情境 | 有效結果 | 有效結果平均絕對誤差 |
| --- | --- | --- |
| 45／72／120／180 BPM，含小雜訊 | 各10／10 | 0.1／0／0／0.5 BPM |
| 真值72，一路加入較強126 BPM動作干擾 | **10／10** | **0 BPM** |
| 真值72，兩路都加入較強126 BPM動作干擾 | 0／10，拒絕 | 不適用 |
| 真值120，動作也是120 | 0／10，因不可區分而拒絕 | 不適用 |
| 單路孤立尖峰 | 10／10 | 0 BPM |
| 低頻基線漂移 | 9／10 | 0.44 BPM |
| 振幅改變 | 10／10 | 0 BPM |
| 中途1秒缺口 | 重置及再暖機後8筆有效 | 0 BPM |
| 平線、缺少ACC、無接觸、極端飽和值 | 無有效輸出 | 不適用 |

另以3個噪聲seed、3組心率／動作頻率檢查有效輸出沒有>8 BPM誤差；也檢查16-bit時鐘回繞。
這些都是開發用合成檢查，不是盲測資料集，也沒有統計證明真實運動準確度。

同時回放既有 `ppg_hr.h` 作比較：單路運動干擾時舊版沒有有效結果；兩路同受126 BPM干擾時，
舊版有4筆新結果且平均誤差53 BPM，新版拒絕。另一方面，同頻動作案例舊版數字恰好正確，新版犧牲可用率以避免無法區分的結果。
舊版為10秒輸出＋首10秒暖機，新版為5秒輸出＋首5秒暖機，兩者筆數不能直接當成同一分母的準確率比較。
CSV中的 `old_bpm` 可能是前一次結果；只有 `old_fresh=1` 代表本筆時間有新的舊版結果。

現有真實錄製：

- `hr1.csv`：4／6個輸出有效（含暖機），心率56、72、60、59。
- `hr2.csv`：11／13個輸出有效（含暖機／缺口後再暖機），有效值65–80 BPM。

原始CSV沒有同步ACC、活動標記、獨立ECG心率真值，所以使用PPG-only模式。
這只能確認實際波形可以回放，不能宣稱新演算法在這兩份錄製比較準。
所有逐窗結果及統計都保存在 `test_results/`。

## 建置與重跑

```powershell

python firmware/n76e003/application/ble_sensor_hr/test_motion_hr.py --out NEW_TEST_DIRECTORY
python firmware/n76e003/application/ble_sensor_hr/profile_motion_hr.py --out NEW_PROFILE_DIRECTORY
```

兩個Python程式只用標準函式庫；host檢查需gcc，profile另需已安裝的Nuvoton SDCC／s51。
本機Python可用 `C:/Users/Song-Hao Lee/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe`，PowerShell以 `& '完整路徑'` 執行。
輸出目錄必須是新目錄，避免覆蓋既有驗證資料。

沒有自動燒錄或修改MCU Config。燒錄ICP／BM7701共用腳位注意事項同 `ble_sensor_capture/README.md`。

## 目前界線

這一版能在部分通道污染時繼續估測、避免一些明顯步頻誤判，但沒有LMS、FFT或完整訊號分離。
三軸過零法對非週期動作、衝擊、加速度量不到的皮膚形變及光學接觸變化可能失效。
週期相近也可能保守地拒絕真正心率；兩路共同假脈搏如果沒有被ACC辨識，仍可能誤報。
門檻尤其ACC強度、週期與諧波容差尚需多人佩戴資料校準。不可把合成結果當成跑步準確率保證。
